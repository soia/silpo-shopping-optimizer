# Silpo MCP — what the API actually does

Findings from the live server (`silpo-mcp-service v1.107.2`, protocol
`2025-06-18`), gathered with real `tools/list` and `tools/call` requests.
Full schemas: [mcp-tools.md](mcp-tools.md) · raw dump: [`data/mcp-tools.json`](../data/mcp-tools.json).

All 39 documented tools exist under the documented names.

## Where the brief and the API disagree

The brief was written from the published documentation. Three of its assumptions
do not hold, all confirmed by schema and by live calls.

**1. `silpo_update_shopping_cart` does not change cart contents.** It updates
delivery, slot, address, promo code, payment and bonuses. Replacing an item is
`remove_cart_products` followed by `add_or_update_cart_products`.

**2. `silpo_get_similar_products` takes a `slug`, not a `productId`** — and also
requires `branchId`. Slugs cannot be constructed: the tool description states
they are generated by Silpo and must come from a previous response. Cart lines
do include `slug`, so no extra lookup is needed.

**3. `add_or_update_cart_products` needs `productId` + `companyId` + `branchId`**
for every product, not just the product id. All three must be carried through
the pipeline from search to write.

## Behaviour that only shows up on live calls

### `update_shopping_cart` demands the whole cart state

Applying just a `promoCode` or `bonusRequested` still requires `deliveryType`,
`timeslot`, `address` and `shipments`. The cart must be read and mirrored back
with one field changed. The tool description is explicit that `address` and
`shipments` are to be copied verbatim rather than constructed.

### An expired timeslot poisons the promo context

A cart whose slot is in the past reports:

```json
"calculation": { "validations": [
  { "level": "error", "type": "timeslot", "message": "timeslot.not_found" }
]}
```

Promo tools require `timeslotStart`/`timeslotEnd` sourced from that same cart, so
the pipeline refreshes the slot from `get_time_slots` first.

It also poisons availability: with the slot in the past, every cart line comes
back with `stock: 0` and its own `product: error` validation. Cart stock is
therefore only trustworthy while the slot is valid.

### Product shape

```json
{
  "id": "1ed0764a-…",
  "name": "Шоколадний батончик Snickers Super+1 зі смаженим арахісом",
  "slug": "shokoladnyi-batonchyk-snickers-…-664167",
  "price": 59.99,
  "oldPrice": 66.49,
  "stock": 16,
  "available": true,
  "weighted": false,
  "step": 1,
  "companyId": "1ec88c5d-…",
  "branchId": "1edb7358-…",
  "externalProductId": 664167
}
```

`price` is the current price with any promotion already applied; `oldPrice` is
the pre-discount price, or `null` when the item is not on promotion. That pair
gives the discount deterministically, with nothing left to infer.

**Missing: `brand`, `category`, and any size or volume field.** Cart lines carry
`ratio` (`"112,5г"`, `"0,33л"`), but search results never do — see
[engine-findings.md](engine-findings.md).

### Search availability and cart availability disagree

`silpo_get_similar_products` can return a product with `available: true` and a
non-zero `stock`, and that same product lands in the cart flagged **«Очікується»**
under *«Деякі товари розкупили»*.

Part of it is structural: when the cart's slot has expired the pipeline searches
against a freshly picked slot, so candidate availability is computed for a slot
the cart does not actually hold.

The cart is the authority. Availability is therefore re-checked after the item is
added — the same round trip the size guard uses — and a line that comes back with
`stock: 0` while the original still reports stock is rolled back.

### `similar_products` returns the original itself

A lookup by the Snickers slug returned 75 products with the same Snickers first.
Candidates must be filtered on `candidate.id !== original.productId`.

Result quality is adequate: that lookup surfaced Kit Kat at 41.99 and Nuts at
31.99 against an original of 59.99 — genuine equivalents, not noise.

### `get_promotions` returns campaigns, not per-product discounts

```json
{ "code": "additional",  "title": "Додаткові пропозиції", "productCount": 5406 }
{ "code": "only_online", "title": "Тільки Онлайн",        "productCount": 1999 }
{ "code": "melkoopt",    "title": "Гуртом дешевше",       "productCount": 668 }
```

These codes feed `get_products(promotionCode)`. A specific product's discount
lives in `price`/`oldPrice`, so "promotions used" is counted as the number of
accepted replacements whose `oldPrice` is set.

## Errors and limits

| Condition | Handling |
|---|---|
| `401 invalid_token` | Refresh token grant; if that fails, prompt to reconnect |
| `403` | Token valid but the tool is not permitted |
| `429` | Exponential backoff with jitter, up to 5 attempts |
| `5xx` | Same backoff path |
| `-32601` | JSON-RPC method not supported by this protocol version |

Rate limiting is applied per user. Streamable HTTP may answer with either
`application/json` or `text/event-stream`; both are parsed. This server does not
issue an `Mcp-Session-Id`.
